# Голосовые сообщения и настройки локального ИИ

**Статус:** техническое задание для интеграции в основной проект. Описанные ниже функции ещё не считаются реализованными. Документ можно передать в другой чат вместе с исходным проектом.

## Что нужно получить

В тренажёре есть два разных сценария работы со звуком:

1. **Предгенерация при создании билета.** Реплики руководителей бригад готовятся заранее. Скорость здесь менее важна, чем связность текста и качество речи. Готовые файлы хранит учебный сервер и доставляет рабочим местам.
2. **Разговор оператора 112 в реальном времени.** Ученик говорит в микрофон, локальный компьютер распознаёт речь, формирует ответ персонажа и тут же озвучивает его. Здесь важна задержка. Каждый рабочий ПК выполняет эту цепочку у себя; сервер не генерирует каждую реплику за все ПК.

Генерация речи в реальном времени на мобильных устройствах **не поддерживается**. Мобильное устройство может воспроизводить уже готовые записи, если это предусмотрено его интерфейсом.

## Роли моделей

| Задача | Модель | Что делает |
| --- | --- | --- |
| Содержание и поведение персонажа | Qwen3 4B Instruct, рекомендована; Qwen3 0,6B, быстрее, но чаще ошибается | Составляет или уточняет текст реплики, определяет, кто говорит, выбирает манеру речи и поддерживает факты одного разговора. **Аудиофайл сама не создаёт.** |
| Распознавание микрофона | Whisper base, точнее; Whisper tiny, быстрее | Преобразует речь пользователя в текст. |
| Синтез речи | Silero v5, быстрее; Qwen3-TTS 1.7B, выразительнее | Превращает готовую фразу в звук с подходящим голосом. |

При генерации LLM должна выдавать структурированный результат: `speaker_id`, роль/имя говорящего, точный текст, пол/тип голоса, эмоциональное состояние (например, спокойствие, паника, уверенность), темп и при необходимости короткую ремарку для интонации. TTS получает только утверждённую фразу и доступные ей параметры голоса. Если модель TTS не поддерживает отдельный параметр эмоции, нельзя обещать точное воспроизведение эмоции: подобрать доступный голос и интонацию, а остальную выразительность оценить на прослушивании.

## 1. Предгенерация при создании билета

### Сценарий автора

1. Преподаватель или администратор добавляет в билет сообщения и звонки руководителей бригад. Основа генерации — утверждённые факты билета: происшествие, адрес, служба, состав бригады, хронология и уже заданные реплики. Модель не должна придумывать факты, противоречащие карточке.
2. У входящего звонка голос обязателен. Текстовое сообщение остаётся текстовым; при необходимости автор отдельно включает для него озвучку. В обоих случаях текст сообщения хранится как доступная для чтения расшифровка.
3. Qwen3 4B Instruct готовит текст и параметры говорящего для новых реплик. Если автор уже написал текст, его нельзя незаметно переписывать: модель может предложить вариант, который автор принимает или отклоняет. Голос одного и того же руководителя должен оставаться одинаковым в пределах билета.
4. После сохранения реплик запускается фоновая задача синтеза. Пока автор проверяет остальные части билета, в небольшом ненавязчивом индикаторе показывается: **«Идёт генерация звуков для сообщений руководителей бригад»**, а также число готовых записей и ошибки. Редактор остаётся доступным.
5. Автор может прослушать готовые записи, изменить текст или голос, перегенерировать только нужную запись и сохранить билет. Перед использованием билета система явно показывает, какие обязательные записи ещё готовятся или завершились ошибкой.

Для фоновой предгенерации по умолчанию использовать Qwen3 4B Instruct для текста и Qwen3-TTS 1.7B для выразительной озвучки, если оборудование справляется. На слабом CPU администратор выбирает Silero v5. Выбор вычислительного устройства CPU/GPU делается отдельно для LLM и TTS. Вычисление может выполняться на сервере или выделенном существующем ИИ-воркере; авторитетная копия аудио хранится на сервере.

### Версии и данные

Аудио привязывается к **конкретной версии билета и конкретному событию**, а не только к названию билета. Для каждой записи нужны: ID события, ID говорящего/контакта, канал события, текст, параметры голоса, использованные модели и их версии, статус `pending/running/ready/failed`, длительность, MIME-тип, размер и SHA-256 файла. Хранить медиа отдельно от JSON билета; в версии билета оставить ссылку на медиа и параметры сценария.

При изменении текста, голоса или параметров TTS устаревшая запись помечается к перегенерации. Неизменённые записи повторно не синтезируются. Уже опубликованная версия и её медиа должны оставаться доступными для начатых занятий; новая редакция получает собственные ссылки на записи. Сохранять исходный текст рядом со звуком, чтобы его можно было показать при проблемах воспроизведения.

Публикация не должна скрывать незавершённый синтез. Если для версии требуется голос и он не готов, показывать автору понятный статус; запуск задания с обязательным звонком разрешать после готовности его аудио. Ошибку генерации можно исправить повторной попыткой, не переделывая билет целиком.

### Доставка и сверка на рабочих местах

Сервер предоставляет авторизованным рабочим местам манифест опубликованных версий билетов и необходимых звуковых файлов. При запуске приложения, восстановлении соединения, появлении новой версии и периодически во время работы ПК сверяет **ID версии и хеши файлов**, скачивает только недостающие или изменённые записи в фоне и проверяет SHA-256 перед переносом в постоянный кэш. Передача должна быть возобновляемой после обрыва и не мешать активному разговору оператора. При отсутствии сети уже проверенные файлы можно воспроизводить из кэша.

Звуки отправляются всем авторизованным подключённым ПК, которым доступен соответствующий опубликованный билет. Фоновая доставка **не запускает воспроизведение**: нужная запись проигрывается только в момент события сценария. Нужны статусы синхронизации и повторная попытка при ошибке. Не стоит переносить большие файлы в каждый короткий запрос состояния: манифест и загрузку медиа сделать отдельными операциями.

В режиме **«Запустить на одном ПК»** действует прежнее правило демоверсии: при новой демосессии данные, билеты и их звуковой кэш загружаются с начала. В режиме локальной сети названия, билеты, медиа и синхронизированный кэш сохраняются между перезапусками согласно обычному хранению проекта.

## 2. Живой разговор оператора 112

На каждом поддерживаемом рабочем ПК цепочка выполняется локально:

`микрофон → Whisper → текст вопроса → Qwen3 Instruct + факты билета и память звонка → текст ответа и параметры персонажа → Silero v5 или Qwen3-TTS → динамик`.

У звонящего должны сохраняться имя, местоположение, обстоятельства и уже установленные факты в рамках текущего звонка. На новый вопрос модель может добавить правдоподобную деталь, совместимую с билетом, и занести её в память звонка. Она не должна повторять вопрос ученика вместо ответа, менять уже названные факты или говорить от лица диспетчера. Если вопрос непонятен, персонаж просит повторить или честно говорит, что не знает ответа.

Чтобы ожидание не выглядело обрывом связи, можно включить короткие **заранее записанные** реплики вроде «Сейчас посмотрю» или «Подождите секунду». Они запускаются только если основной ответ не готов через **1,5 секунды** после окончания вопроса (значение настраивается). Реплика должна соответствовать персонажу и не подменять содержательный ответ. После готовности ответа вставка завершается и начинается основной звук. При завершении звонка незаконченная генерация отменяется.

**Рекомендуемое начальное сочетание для скорости:** Whisper tiny или base по возможностям ПК, Qwen3 4B на GPU при наличии подходящей видеокарты (либо Qwen3 0,6B на слабом ПК), Silero v5 для речи. Qwen3-TTS 1.7B оставить доступной как экспериментальный выбор для живого режима с явным предупреждением о возможной большой задержке. В отдельном прототипе `F:\AI\VoicePhoneLab` на одном тестовом ПК Qwen3-TTS формировала примерно 5 секунд звука за ~13,7 с на GPU и ~19,4 с на CPU; Silero произносила короткую фразу существенно быстрее. Это ориентир, а не гарантия для других ПК. Прототип не интегрирован в основной проект.

**Дополнительный опыт с моделями диалога.** В отдельном прототипе проверены Phi-4 mini 3,8B и Gemma 3 4B на тех же семи русских репликах. Phi-4 mini показала медиану 6,66 с на CPU и 0,83 с на GPU против 6,55/0,69 с у Qwen3 4B; её можно предложить как экспериментальную альтернативу в настройках рабочего ПК. Однако она употребила мужской род для женского персонажа и на CPU предложила городской номер вместо мобильного. Gemma 3 4B была медленнее: 10,36/1,48 с и допустила противоречие в возрасте. Поэтому рекомендацию по умолчанию менять рано. Подробности и полные ответы: `F:\AI\VoicePhoneLab\MODEL_COMPARISON.md` и `output/dialogue-model-comparison-new.json`.

Позднее в прототип добавлены и проверены ещё четыре модели: Ministral 3 3B, GigaChat 3.1 Lightning, LFM2.5 1,2B и SmolLM3 3B. В коротком русском сценарии GigaChat дала наиболее связные ответы из этих четырёх; медиана текста составила 7,59 с на CPU и 0,58 с на GPU после запуска, но первый ответ был заметно длиннее. Её файл весит 6,47 ГБ. LFM2.5 и SmolLM3 отвечали быстро, но путали смысл и роль заявителя. Ministral несколько раз требовала повторной генерации. Полные результаты: `F:\AI\VoicePhoneLab\MODEL_COMPARISON.md` и `output/dialogue-model-comparison-four.json`. Эти варианты доступны для тестирования, выбор для основной программы следует делать после более длинных разговоров с живым микрофоном.

## 3. Настройки: отдельная группа «Генерация звука»

Разделить экран на **«Предгенерация для билетов»** и **«Генерация в реальном времени»**. Настройки администратора для сервера и настройки конкретного рабочего места должны различаться: оборудование у ПК разное. Недоступный GPU или отсутствующая модель должны показываться как недоступный вариант с причиной, а не приводить к незаметному сбою.

| Раздел | Настройка | Варианты / поведение |
| --- | --- | --- |
| Предгенерация | Модель анализа и подготовки реплик | Qwen3 4B Instruct — рекомендована; Qwen3 0,6B — быстрее. |
| Предгенерация | Устройство модели анализа | CPU / GPU. |
| Предгенерация | Модель озвучки | Qwen3-TTS 1.7B — качество; Silero v5 — скорость и слабый CPU. |
| Предгенерация | Устройство озвучки | CPU / GPU. |
| Предгенерация | Очередь и просмотр | Количество готовых записей, ошибка, повторить, прослушать, перегенерировать. |
| Реальное время → анализ | Модель диалога | Qwen3 4B Instruct — начальный выбор; Qwen3 0,6B — быстрее, но чаще ошибается; Phi-4 mini 3,8B и GigaChat 3.1 Lightning — проверенные экспериментальные альтернативы. Ministral 3 3B, LFM2.5 1,2B и SmolLM3 3B пока оставить в прототипе для сравнения. |
| Реальное время → анализ | Устройство модели | CPU / GPU **этого рабочего ПК**. |
| Реальное время → распознавание | Модель | Whisper base — точнее; Whisper tiny — быстрее. |
| Реальное время → распознавание | Устройство | CPU / GPU этого ПК. |
| Реальное время → распознавание | Проверить микрофон | Записывает короткий тест и показывает **распознанную фразу**; желательно показать время распознавания. |
| Реальное время → озвучка | Модель | Silero v5 — рекомендуемая для скорости; Qwen3-TTS 1.7B — выразительнее, но может отвечать долго. |
| Реальное время → озвучка | Устройство | CPU / GPU этого ПК; отдельная кнопка прослушивания тестовой фразы и измерение времени. |
| Реальное время → ожидание | Короткие готовые реплики | Вкл./выкл.; задержка перед вставкой — **1,5 с по умолчанию**. |

Рядом с выбором моделей показывать фактически загруженную модель, доступность весов и измеренную на данном ПК задержку тестовой реплики. CPU/GPU должны выбираться **отдельно** для распознавания, диалога и синтеза. На мобильных пункты живой генерации отключены с пояснением «Генерация речи в реальном времени на мобильных устройствах не поддерживается».

## Точки интеграции в существующем проекте

- `apps/web/src/tickets.tsx`: редактор уже хранит `service_events` с каналами `message` и `incoming_call`, текстом, временем, `contact_id` и говорящим. Добавить предпросмотр, состояния генерации и привязку аудио к голосовым событиям. Не возвращать громоздкие настройки озвучки внутрь формы билета: они находятся в отдельной группе настроек.
- `apps/api/app/schemas.py`: у задачи есть `service_events`, `intro_audio` и `Question.audio_id`; у событий бригад отдельного `audio_id` пока нет. Добавить проверяемую схему связи события со звуком и правила для голосовых/текстовых каналов.
- `apps/api/app/db.py`: уже есть `TicketVersion` и `Media`. Понадобятся задания фоновой генерации, метаданные результата и манифест синхронизации либо эквивалентные структуры. Не складывать бинарные файлы в JSON версии билета.
- `apps/api/app/main.py`: текущие `/api/media` предназначены прежде всего для ручной загрузки, а доступ учащегося к аудио зависит от его попытки. Для фоновой синхронизации нужны отдельная серверная запись сгенерированного файла и авторизованная выдача рабочим местам. Валидацию публикации дополнить проверкой нужных звуков.
- `apps/web/src/workspace.tsx` и поток занятия: уже есть воспроизведение аудио по ID медиа; подключить готовые записи к событиям бригад и локальный голосовой движок к 112, сохранив текстовую расшифровку.
- `local_ai/manifest.json`: в основном проекте уже перечислены Qwen3 4B Instruct и Qwen3 0,6B. Веса моделей не следует предполагать установленными только потому, что они указаны в манифесте. Отдельный прототип `F:\AI\VoicePhoneLab` можно использовать как источник проверенного поведения и замеров, но не считать готовым модулем основного приложения.

## Проверка готовности

1. Создать билет с двумя звонками одного руководителя: реплики звучат одним голосом, текст на экране совпадает с произнесённым. Обычное текстовое сообщение не проигрывается само по себе.
2. Пока автор редактирует другие поля, виден ненавязчивый статус фоновой генерации. Ошибка одного файла не уничтожает остальные; доступна повторная попытка.
3. Изменение одной реплики создаёт новый звук только для неё; занятие по старой опубликованной версии продолжает использовать старый файл.
4. Второй рабочий ПК после подключения получает недостающие звуки, проверяет хеши и воспроизводит запись в нужный момент. После обрыва загрузка возобновляется без повторной передачи всех файлов.
5. При запуске и после обновления билета манифест и локальный кэш сходятся; при временной потере сети готовые записи остаются доступными.
6. Тест микрофона показывает распознанную фразу. При живом звонке слышен ответ персонажа на вопрос ученика, а не повтор вопроса; факты сохраняются между репликами.
7. На CPU и GPU можно отдельно проверить и увидеть фактическое время распознавания, ответа модели и синтеза. Без GPU интерфейс не предлагает неработающий режим.
8. На мобильном устройстве живые настройки и запуск генерации недоступны, готовые записи воспроизводятся при наличии соответствующего сценария.
9. Новая демосессия на одном ПК начинает загрузку билетов и звуков заново; локальная сеть сохраняет данные и кэш после перезапуска.

## Порядок реализации в другом чате

1. Уточнить формат события и медиа, добавить фоновые задачи генерации и сохранение по версиям билета.
2. Сделать генерацию/прослушивание сообщений бригад в редакторе и статус задачи.
3. Реализовать манифест, авторизованную доставку и сверку кэша рабочих мест.
4. Подключить локальную цепочку Whisper → Qwen3 → TTS к режиму 112 и память одного звонка.
5. Добавить две группы настроек, тест микрофона, замеры задержек и короткие реплики ожидания; пройти проверки выше на CPU, GPU, втором ПК и мобильном интерфейсе.
