# Решения первой реализации

Дата: 18.09.2026. Дополняет «Основу ТЗ и архитектуру тренажёра 112». Предметный приоритет исходных документов и уточнений пользователя сохраняется. Ни одно из решений ниже не приписывается официальному ТЗ.

1. **Веб-приложение в локальной сети.** React + TypeScript + Vite, FastAPI + SQLAlchemy, PostgreSQL. Клиент получает статическую сборку с того же сервера; внешних CDN и шрифтов нет. Отдельный Windows-инсталлятор и нативное приложение телефона не требуются для запуска базовой версии.
2. **Обновления через REST и периодический снимок.** В первоначальной архитектуре предлагался SSE. На первом этапе используется опрос каждые 2 секунды для попытки и 5 секунд для назначений. Источник истины — сервер и БД. События долговечны, переподключение загружает сохранённое состояние. Для дальнейшего SSE можно оставить те же команды и заменить транспорт уведомлений.
3. **Без дополнительных библиотек форм и запросов.** На данном объёме используются контролируемые React-формы, общий API-клиент и hook загрузки. Локальная несохранённая карточка не подменяется фоновыми ответами сервера. TanStack Query и React Hook Form из предварительного стека не добавлены.
4. **Схема БД управляется Alembic.** Начальная миграция фиксирует таблицы. Новые изменения нужно оформлять отдельными ревизиями; `create_all` не заменяет миграции при эксплуатации.
5. **SQLite — дополнительный режим одиночной демонстрации и тестов.** Основной подготовленный контур использует PostgreSQL. SQLite не объявляется эквивалентом PostgreSQL для конкурентной работы класса.
6. **У каждой учётной записи одна роль.** Администратор имеет функции преподавателя по всем группам плюс управление контентом/пользователями. Право аудита независимо от роли. Преподаватель ограничен своими группами. Многоролевые профили и несколько преподавателей одной группы можно добавить отдельной миграцией.
7. **112 и ДДС — отдельные задачи.** В 112 другие службы отвечают автоматически; оператору не нужно ждать реального окончания работ. В ДДС обучаемый регистрирует действия своей службы. «Получена службой» не равна «Принята». Причина непринятия/отказа обязательна. Переходы вперёд допускают пропуск промежуточного этапа, конечные статусы блокируют дальнейшую запись.
8. **Симуляция хранится в БД.** Один worker внутри серверного процесса применяет события по времени. Не запускайте несколько несогласованных учебных серверов на одной базе при использовании SQLite. В PostgreSQL обработка использует блокировки; перед горизонтальным масштабированием всё равно нужны отдельные нагрузочные проверки.
9. **Проверка прозрачная и детерминированная.** Поля/вопросы/службы/статусы/время проверяются по критериям версии; смысл свободного текста оценивает преподаватель. Балл до ручной проверки предварительный. Статистика ошибок — агрегация, не ML. Наличие лишней оповещённой службы автоматически не штрафуется: используйте отдельную ручную проверку обоснованности.
10. **Начальный контент ограничен пятью демонстрационными билетами.** Три ситуации 112 и две ДДС. Полный банк из исходного PDF не выдаётся за готовый проверенный учебный набор. Добавление остальных билетов выполняется через готовый редактор после подготовки и согласования эталонов.
11. **Классификатор импортирован как справочник.** Сохраняются 1 283 типа, признаки, исходная строка и SHA-256 файла. Условные столбцы маршрутизации XLSX автоматически не исполняются. Список ожидаемых служб задаётся автором в рубрике билета.
12. **Визуальная точность относится прежде всего к рабочему АРМ.** Воспроизведены основные группы, две колонки, плоские серые поля, телефонные поля сверху, оранжевая панель оповещения 112 и тёмная/синяя панель служб ДДС. Кабинеты и редактор собственные. Реальные карты, запись разговоров, SMS и другие функции боевого АРМ, не реализованные тренажёром, не представлены декоративными работающими кнопками.
13. **Явное сохранение карточки.** Кнопки оповещения и завершения предварительно сохраняют текущий ввод. Браузер предупреждает при перезагрузке с несохранёнными изменениями. Автоматическая запись каждого символа не реализована; аудит хранит подтверждённые изменения и значимые UI-действия.
14. **Без речевых моделей и VR.** Вопросы выбираются из подготовленного перечня; ответ — текст и, если добавлено автором, аудио WAV/MP3. Файлы физически хранятся на сервере, доступ проверяется API. На телефоне панель связи сворачивается.
15. **Аудит прикладной.** Команды и изменения пишутся транзакционно вместе с результатом; клики/навигация отправляются браузером. Входы, отказ входа, изменения пользователей и контента фиксируются. Это не внешнее неизменяемое хранилище: администратор БД технически может менять таблицы. Доставка чисто UI-событий при обрыве сети не гарантируется; изменения данных подтверждаются только сервером.

Структура файлов, команды запуска, роли и ограничения описаны в `README.md`. Развитие речи следует делать через адаптер входного вопроса и источник ответа, сохраняя существующие Attempt/Command/Assessment. Развитие классификатора — отдельный модуль проверяемых правил с источниками и тестами, а не эвристическое чтение непустых ячеек XLSX.
