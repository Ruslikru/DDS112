# Основной сценарий и уточнения ТЗ — версия 0.4.0

Актуализация от 24 сентября 2026 года. Основание: исходное ТЗ заказчика («Учебное программное обеспечение для подготовки оператора ДДС»), инструкции АРМ-112 и ответы заказчика, переданные пользователем в переписке. При расхождении с прежней выжимкой по ДДС применяется этот документ. Последние вопросы участников чата, на которые ещё нет ответа заказчика, не считаются требованиями.

## Приоритеты

Основной пользователь — диспетчер ДДС. Основной результат — отработка реагирования по заполненным карточкам: решение о принятии, связь, статусы, комментарии, временные нормативы, несколько происшествий одновременно. Генерация сценариев и оценка помогают организовать обучение, но не заменяют сам рабочий процесс.

Режим оператора 112 сохраняется: эмуляция его работы прямо указана в постановке задачи. В нём ученик опрашивает заявителя, заполняет карточку и оповещает службы. Это отдельный режим, а не обязательный предварительный этап каждой тренировки ДДС.

Голосовые модели, реальная телефония и VR в эту итерацию не входят по согласованному ограничению пользователя. Общение текстовое, всё выполняется локально.

## Рабочий процесс ДДС

1. Преподаватель выбирает опубликованные билеты ДДС, учеников и интервал поступления. Запускает занятие.
2. Карточки поступают независимо от того, какая карточка сейчас открыта. Отдельный норматив первичного решения начинается с доставки каждой карточки. В очереди видны время, статус и превышение норматива.
3. Диспетчер принимает карточку своей службой либо обосновывает непринятие. Входящие поля карточки доступны для чтения.
4. При необходимости связывается со старшим бригады, заявителем или другой службой-получателем, если её телефон задан в сценарии.
5. Получает входящие доклады или сам уточняет ход работ. Доклады не меняют статус его ДДС автоматически.
6. Вносит статусы и комментарии, завершает обработку, продолжает работу с очередью. Преподаватель может завершить занятие для всех.

ДДС не выполняет контроль правильности заполнения карточки оператором 112 и не добавляет получателей карточки. Соответствующий обязательный блок проверки убран. Старые результаты и опубликованные версии сохраняются для истории; демонстрационный билет взаимодействия с бригадой получил новую версию.

Поток работает по серверному времени, переживает перезапуск. Доставка имеет уникальный ключ в БД, чтобы повторная обработка расписания не дублировала карточки. В потоке индивидуальная пауза отключена: другие карточки продолжают ожидать решения. Интервал задаётся преподавателем; число «раз в минуту, не больше трёх» из вопроса участника не объявляется обязательным ограничением заказчика.

## Генерация карточек и ответов

По умолчанию генератор создаёт ДДС-сценарий. Автор выбирает тип из исходного классификатора, свою службу, район, подчинённость и других получателей; описывает ситуацию.

Локальная модель создаёт вымышленные обстоятельства, имя, адрес и сведения о пострадавших. Приложение собирает единую входящую карточку, контакты, доклады и критерии из этих данных. Этапы реагирования формируются последовательными правилами: выезд, прибытие, работы, завершение. Это предотвращает противоречия свободной генерации стадий. Автор может изменить тексты и сроки в редакторе.

Сценарий сохраняется как черновик. До назначения ученикам требуется проверка и публикация преподавателем. Проверка структуры и принадлежности типа классификатору не доказывает предметную корректность любого текста модели. География вымышленного адреса, полномочия конкретной службы, получатели и специальные действия требуют предметной проверки. Автоматический официальный географический маршрутизатор не реализован и не заявляется.

В разговорах модель распознаёт смысл запроса, а факты выдаются из сценария. Вопрос о текущем ходе работ не продвигает время и не вызывает досрочное прибытие бригады. Автор может добавить вопросы и ответы отдельно для каждого абонента. Модель не учится автоматически на действиях учеников и не заменяет эталон собственными догадками.

## Оценка

Автоматически оцениваются заданные критерии: решение, наличие требуемых статусов, связь с нужным абонентом, время от поступления до первого решения. С версии 0.6.0 свободные комментарии автоматически оценивает локальная модель с начислением предварительных баллов и объяснением. Преподаватель может исправить оценку. Подробности: [проверка комментариев 0.6.0](ИИ_проверка_комментариев_0.6.0.md).

Приходящие сообщения и выставленные статусы — разные сущности. Для демонстрации текстовый звонок привязан к учебной карточке; это не заявление об автоматическом выборе карточки при реальном телефонном звонке. Этот вопрос остаётся не до конца разъяснённым заказчиком.

## Реализация

- `apps/api/app/dds_flow.py`: доставка карточек, неизменяемые снимки попыток и время поступления.
- `apps/api/migrations/versions/0004_stream_delivery.py`: уникальный ключ доставки; сохраняет прежние попытки.
- `apps/api/app/extensions.py`: занятия, управление потоком, очередь и доступ преподавателя/ученика.
- `apps/api/app/dds_scenarios.py`: сборка карточки, контактов, этапов и рубрики из общих фактов.
- `apps/api/app/ai_routes.py`, `caller.py`: локальная генерация и распознавание вопросов без свободной подмены фактов.
- `apps/api/app/main.py`: команды диспетчера, входящие звонки, ручные статусы, аудит.
- `apps/web/src/dds-queue.tsx`, `workspace.tsx`: очередь, карточка, телефон и журнал.
- `apps/web/src/ai.tsx`, `lessons.tsx`, `tickets.tsx`: генератор, настройка потока и редактор сценария.

Технологии сохранены: FastAPI/SQLAlchemy/Alembic, React/TypeScript, SQLite в настольной сборке, поддержка PostgreSQL в серверном варианте, pywebview/WebView2 для EXE, локальные Qwen3-4B и llama.cpp. Внешний API для работы этой версии не требуется.

## Как проверить

1. `teacher` или `admin`: библиотека → «Создать ситуацию с нейросетью» → режим ДДС → заполнить параметры → проверить черновик → опубликовать.
2. Занятия → подготовить занятие → «Поток карточек ДДС» → выбрать только билеты ДДС и учеников → задать интервал → сохранить → начать.
3. `student`: занятия → продолжить → открыть карточку из очереди → нажать плитку своей службы → записать решение.
4. Выбрать старшего бригады, передать заявку. Принять последующие входящие звонки; самостоятельно записывать соответствующие статусы и комментарии.

Проверено 17 автоматических тестов, включая поток, задержки, повторную доставку, доступы, входящие доклады, ручное управление статусами, генерацию и сохранение роли 112. Проведены проверки настоящей локальной модели (`local_ai/check_dds.py`, результат `local_ai/dds-check-results.json`) и интерфейса через Playwright. Обновление копии существующей пользовательской базы до миграции 0004 сохраняет прежние попытки без изменений.

Полное соответствие всему ТЗ не сертифицировано. Не проверены нагрузка 100 пользователей/20 одновременных сессий и скорость на минимальном оборудовании заказчика; текущая модель обрабатывает запросы последовательно. Звук/VoIP/VR отложены. Предметную корректность произвольных сгенерированных сценариев должен подтверждать методист. Дополнительные формы типов происшествий и неразъяснённые аспекты интерфейса реального телефона нельзя восстанавливать догадками.
